01

SOLID elvek

Az öt SOLID elv a jól tervezett, karbantartható OO kód alapköve. Mindegyik egy oksági elvben foglalja össze, mikor és miért változzon egy osztály.

S – Single Responsibility Principle (SRP)

Egy osztálynak egyetlen felelőssége legyen – csak egy ok miatt változhasson.

Példa: A riport összeállítása és nyomtatása két különböző ok miatt változhat → két különböző osztály.

  • Erős kohézió (cohesion) és laza csatolás (coupling) az eredmény
  • Robosztusabb, átláthatóbb, jobb tesztelhetőség

O – Open/Closed Principle (OCP)

A komponens legyen nyitott a bővítésre, de zárt a módosításra. Anélkül tudjuk bővíteni, hogy a meglévő kódhoz hozzá kellene nyúlni.

// ROSSZ: minden új alakzatnál módosítani kell
if (s instanceof Rectangle) area += r.a * r.b;
else if (s instanceof Circle) area += c.r * c.r * PI;

// JÓ: interfész-alapú, bővítés új osztállyal
interface Shape { double area(); }
area += s.area(); // minden Shape-re egységesen

L – Liskov Substitution Principle (LSP)

Az objektumokat leszármazott osztályukkal felcserélhetjük a helyes működés megsértése nélkül.

Technikai polimorfizmus ≠ LSP; a viselkedésnek is meg kell felelnie (pl. lista valóban tárolja és visszaadja, amit beletettünk).

I – Interface Segregation Principle (ISP)

Az osztály ne függjön olyan interfészektől, amelyeknek metódusait nem használja ki. Használjunk specifikus, kis interfészeket a nagy helyett.

// ROSSZ: BmwX5-nek nem kell setTurnSignal
interface Car { setSeatHeating(); setTurnSignalLeft(); ... }

// JÓ: szétválasztva
interface SeatHeating { setSeatHeating(boolean v); }
class BmwX5 implements SeatHeating { ... }

D – Dependency Inversion Principle (DIP)

Absztrakcióktól függjünk, ne konkrét dolgokból. A függőségeket ne a függő osztály hozza létre, hanem kívülről kapja (→ Dependency Injection).

  • Interfészek/absztrakt osztályok a függőségekhez
  • Konstruktor- vagy setter-paraméterként adják át az implementációt

Kapcsolódó elvek

KISS

Keep it simple stupid – feleslegesen ne bonyolítsuk a kódot.

YAGNI

You aren't gonna need it – amíg nem biztos, hogy kell, ne fejlesszük ki.

DRY

Don't repeat yourself – minden feladatot egyszer, egy helyen oldjunk meg.

03

Osztálydiagram

A leggyakrabban használt UML diagram. OOP-alapú rendszerek struktúráját írja le: osztályok, tagváltozók, metódusok, kapcsolatok. Programozási nyelvtől független.

Osztályok szintaxisa

ElemSzintaxisPélda
Tagváltozó[láthatóság] [név]: [típus][mult] [=érték]- balance: int = 0
Metódus/Művelet[láthatóság] [név]([params])[: visszatérés]+ withdraw(amount: int): bool
Statikus tagaláhúzással jelölve- maxId: int
Absztraktdőlt betűvel jelölve+ calculate(): double

Láthatósági jelölések

+ public - private # protected ~ package

Multiplicitás

1 vagy 1..1 0..1 opcionális 0..* vagy * lista n..m tartomány

Kapcsolattípusok

KapcsolatJelölésSzemantikaKódban
Asszociáció folytonos vonal Általános kapcsolat, (részben) navigálható tagváltozó
Általánosítás / Öröklés üres háromszög nyíl az ős felé IS-A, leszármazott kibővíti az őst extends
Interfész megvalósítás szaggatott vonal üres háromszöggel IS-A, interfész implementálása implements
Kompozíció teli rombusz a tartalmazónál HAS-A kizárólagos; törléskor a tartalmazott is törlődik tagváltozó
Aggregáció üres rombusz a tartalmazónál HAS-A megosztott; egységek életciklusa független tagváltozó
Függőség szaggatott nyíl Laza, ideiglenes kapcsolat import / helyi példány
IS-A vs HAS-A emlékeztető: Öröklés/interfész = IS-A (általánosítás, közös funkcionalitás, Liskov-felcserélhetőség). Kompozíció = kizárólagos HAS-A (tartalmazó nélkül nem létezik a tartalmazott). Aggregáció = megosztott HAS-A (más is „tartalmazza"). Asszociáció = sem tartalmazás, sem öröklés.

Egyéb elemek

Enumeráció <<enumeration>>

Felsorolt típus rögzített értékkészlettel (pl. AKTIV | INAKTIV | VARAKSZO).

Sztereotípiák <<stereotype>>

Meglévő elem jelentésének kiterjesztése. Pl. <<interface>>, <<enumeration>>, <<use>> (dependency-nél).

04

Szekvenciadiagram

Az objektumok közötti üzenetek sorrendjére fókuszál. Egy konkrét lefutást ábrázol. Rendszer- és metódusszinten egyaránt alkalmazható.

Alapfogalmak

Életvonal (Lifeline)

Szintaxis: [név]: [típus]

Nem osztályok, hanem példányok szerepelnek. Az idő fentről lefelé telik.

Futási specifikáció

Téglalap az életvonalon – jelzi, hogy az objektum éppen aktív (metódus fut rajta).

Üzenettípusok

TípusJelölésJellemző
Szinkron hívásteli nyílhegy →Blokkolja a hívót, van visszatérési értéke (szaggatott nyíl visszafelé)
Aszinkron hívásnyitott nyílhegy →Nem blokkolja a hívót, nincs kötelező visszatérési érték
Belső hívásönmagára mutatAz objektum saját metódusát hívja
Létrehozás<<create>> sztereotípiávalKonstruktor – az életvonal később kezdődik
MegsemmisítésX az életvonal végénDestruktor – az életvonal véget ér

Kombinált részletek (Combined Fragments)

alt – Alternatív

If-else jellegű elágazás. Feltételek [ ] zárójelben jelölve. Minden feltétel legfeljebb egyszer fut.

loop – Ciklus

Elöltesztelős ciklus feltétel szerint. [min, max] megadható a keretben.

opt – Opcionális

Else ág nélküli if. A blokk csak a feltétel teljesülésekor fut.

par – Párhuzamos

Párhuzamosan végrehajtandó utasítások. Részei bármilyen sorrendben végrehajthatók.

05

Állapotgép (State Machine)

Objektum-orientált, eseményvezérelt „véges automata". Fókusz: a rendszer állapotai és az állapotátmenetek feltételei.

Alapelemek

ElemJelölés
Kezdő állapotTeli kör (●)
ÁllapotLekerekített téglalap
Végső állapotTeli kör körrel (◎)
TerminálásX – azonnal vége, akciók nélkül
ÁtmenetNyíl állapotok között

Átmenet felépítése

trigger [őrfeltétel] / akció

  • Trigger: az átmenet oka (esemény, kódban: külső metódushívás)
  • Őrfeltétel: [ ] zárójelben; triggerek finomhangolása
  • Akció: az átmenet során végrehajtandó kód (belső függvényhívás)

Összetett állapotok és speciális elemek

Összetett állapot

Composite State

Más állapotokat tartalmaz belül. Belépési (entry) és kilépési (exit) akciók futnak be-/kilépéskor.

Régió

Ortogonális régiók

Összetett állapot párhuzamos részekre bontva (fork/join). Mindkét régió párhuzamosan aktív.

Történet

Shallow (H) / Deep (H*)

Visszatéréskor visszaállítja a korábbi belső állapotot. Shallow: egy szint. Deep: bármilyen mélység.

Alállapotgép

Submachine State

Hivatkozás egy másik összetett állapotra. Újrafelhasználás lehetősége.

Elágazás / Egyesítés

Fork / Join

Fork: egyszerre több állapot aktiválódik. Join: megvárja az összes részállapotot.

Be-/kilépési pont

Entry / Exit Point

Nevesített be- és kilépési pontok összetett állapoton. Különböző forgatókönyvekhez.

AktivitásdiagramMunkafolyamat; vezérlési folyam fontosabb az állapotnál

06

Tervezési minták

A GoF (Gang of Four) könyv 23 mintát katalogizált. Célok: könnyen változtatható/kiterjeszthető kód, újrafelhasználhatóság, unit tesztelhetőség.

Kategóriák

Létrehozási

Factory Method, Abstract Factory, Singleton, Builder, Prototype

Strukturális

Adapter, Composite, Façade, Proxy, Bridge, Decorator

Viselkedési

Template Method, Strategy, Observer, Command, Memento, …

Template Method (Sablonmetódus)

Cél: Algoritmusvázat definiál, a lépések implementálását a leszármazottra bízza. Az ős Run() metódusa hívja a virtuális/absztrakt lépéseket.

Osztálydiagram (egyszerűsített)

abstract class DataProcessorBase {
  public void Run() {
    InitCompression();
    while (data != null) {
      CompressData(data);
      if (IsCancelled()) return;
    }
    CloseCompression();
  }
  protected abstract void InitCompression();
  protected abstract byte[] CompressData(byte[] d);
  protected virtual bool IsCancelled() => false;
}
class ZipDataProcessor : DataProcessorBase {
  protected override void InitCompression() { ... }
  // ...többi override
}

Mikor jó? Mikor nem?

✓ Előnyök

  • Kódduplikáció elkerülése (DRY)
  • Könnyen új viselkedés
  • Keretrendszerekben gyakori

✗ Hátrányok

  • Futás közben nem cserélhető viselkedés
  • Sok aspektusnál kombinatorikus robbanás

Strategy (Stratégia)

Cél: Algoritmusok egy csoportján belül az egyes algoritmusokat egységbe zárja és egymással kicserélhetővé teszi. A kliens csak az interfészt látja.

interface ICompressionStrategy {
  void InitCompression();
  byte[] CompressData(byte[] data);
  void CloseCompression();
}
class DataProcessor {
  ICompressionStrategy compressionStrategy;
  ICancellationStrategy cancellationStrategy;
  // konstruktorban kapja meg (Dependency Injection!)
}

✓ Előnyök

  • Futás közben cserélhető viselkedés
  • Több aspektusnál nincs kombinatorikus robbanás
  • Unit tesztelhetőség (dummy strategy)

vs Template Method

  • Strategy: delegál más osztályoknak → rugalmasabb
  • Template Method: leszármazottra bíz → egyszerűbb

Singleton (Egyke)

Cél: Biztosítja, hogy egy osztályból csak egy példány létezzen, és ehhez globális hozzáférést biztosít.

class WindowManager {
  private static WindowManager instance;
  private WindowManager() { } // védett konstruktor
  public static WindowManager GetInstance() {
    if (instance == null)
      instance = new WindowManager();
    return instance;
  }
}

⚠ Sokszor antipattern! Unit tesztelhetőséget rontja. Dependency Injection általában jobb megoldás.

Observer (Megfigyelő)

Cél: Egy objektum (subject) értesítést küld más objektumoknak (observer) az állapotának változásairól – anélkül, hogy a konkrét típusuktól függne.

Szereplők

  • Subject: tárolja az observereket, értesíti őket (Notify())
  • Observer: interfész az Update() metódussal
  • ConcreteSubject: az érdemi állapotot tárolja
  • ConcreteObserver: hivatkozás a subject-re; Update()-ban lekérdezi az állapotot

Szekvencia vázlata

doc  →  Attach(view1)
doc  →  Attach(view2)
—
valaki → doc.SetData(x)
doc  →  Notify()
doc  →  view1.Update()
view1→  doc.GetData()
doc  →  view2.Update()
view2→  doc.GetData()

Előny: könnyen bővíthető új observerekkel; Subject nem függ a konkrét observer típusoktól. A .NET event ennek egy speciális megjelenése.

Composite (Összetett)

Cél: Rész-egész viszonyú objektumokat fastruktúrába rendez. A kliens az egyszerű és összetett objektumokat egységesen kezeli.

interface Graphics { void Draw(); }
class Line : Graphics { void Draw() { ... } }  // Leaf
class Panel : Graphics {                          // Composite
  List<Graphics> children;
  void Draw() { foreach (g in children) g.Draw(); }
  void Add(Graphics g)  { children.Add(g); }
}

Mikor: objektumok rész-egész viszonya + a kliens egységesen akarja kezelni az elemi és összetett objektumokat.

Adapter (Illesztő)

Cél: Egy osztály interfészét olyan interfésszé konvertálja, amilyent a kliens vár – lehetővé téve inkompatibilis interfészek együttműködését.

Object Adapter (preferált)

class EditableTextShape : Shape {
  TextBox textBox; // becsomagolt Adaptee
  override Rect GetBoundingBox() {
    return textBox.GetExtent(); // delegál
  }
}

Class Adapter

Leszármaztatással; Java/C# esetén Target csak interfész lehet (nincs többszörös öröklés). Kevésbé rugalmas.

07

Fejlesztési módszertanok

A módszertan meghatározza a szoftverfejlesztés aktivitásait, sorrendjüket és az azokban résztvevő szerepköröket.

Vízesés modell (Waterfall)

Az elmúlt 50+ év legelterjedtebb modellje. Lineáris – az egyes fázisok egymás után következnek, egy fázis lezárása után lép a következőbe.

1. Követelmény specifikáció → 2. Szoftvertervezés → 3. Megvalósítás & integráció → 4. Tesztelés → 5. Telepítés & karbantartás

✓ Előnyök

  • Egyszerű, könnyen betartható
  • Változások dokumentumokon követhetők
  • Megrendelő nem szükséges folyamatosan
  • Projekt fejlődése könnyen mérhető
  • Hamar megtalált hibák olcsóbbak

✗ Hátrányok

  • „Követelmények nem változnak" – nem realisztikus
  • Nincs visszajelzés az elkészültig
  • Papíron létező spec-et az ügyfél félreérti
  • Változások drágák (újratervezés)
  • Integráció egyetlen nagy feladat a végén
Mikor érdemes? Fix követelmények, ismert technológiák, törvényi határidők, fix projekt alapú megállapodás, megrendelő csak mérföldköveknél van jelen.

Agilis fejlesztés – alapelvek

Az agilis kiáltvány (2001) négy értéke és 12 alapelve. Közös vonás: iteratív, inkrementális fejlesztés, folyamatos visszacsatolás, változásokhoz való alkalmazkodás.

Agilis alapelvek (kiemeltek)

  • Működő szoftver a legjobb haladásmérő
  • Változó követelményeket akár késői stádiumban is elfogadják
  • Rövid szállítási ciklusok (hetek)
  • Üzleti és fejlesztők napi együttműködése
  • Önszervező csapatok
  • Rendszeres visszatekintés (retrospective)

08

Scrum

A legelterjedtebb agilis keretrendszer. Iteratív-inkrementális, önszervező csapatokra épül. Alapegysége a Sprint (2–4 hét).

Szerepkörök

Product Owner

A termék vízióját képviseli. Karbantartja és priorizálja a Product Backlog-ot. Felelős a ROI-ért.

Scrum Master

A Scrum folyamatért felelős. Elhárítja az akadályokat (impediment). Nem projektvezető – szolgáló vezető.

Development Team

Önszervező, keresztfunkcionális csapat (5–9 fő). Ők tervezik és szállítják a Potentially Shippable Increment-et.

Artifaktok

Product Backlog

Prioritás szerint rendezett lista az összes szükséges funkcióról (user story-k). A Product Owner kezeli.

Sprint Backlog

A Sprint Planning-en kiválasztott item-ek + terv a megvalósításhoz. A csapat kezeli.

Potentially Shippable Increment

Minden Sprint végén leszállított, kész, átadható terméknövekmény. „Done" definíció kell hozzá.

Események (Ceremonies)

EseményMikorCélRésztvevők
Release Planning Release előtt Magas szintű terv több sprintre PO, SM, Team
Sprint Planning Sprint elején Sprint cél + Sprint Backlog összeállítása Teljes csapat
Daily Scrum Naponta, max 15 perc Szinkronizáció: mit csináltam, mit fogok, mi akadályoz? Dev Team (+ SM)
Sprint Review Sprint végén Az elkészült increment bemutatása, visszacsatolás Teljes csapat + stakeholders
Sprint Retrospective Review után Folyamat javítása: mi ment jól, mi nem, hogyan javítsunk? Teljes csapat

Sprint folyamata

Product Backlog → Sprint Planning → Sprint Backlog → 2–4 hetes Sprint (Daily Scrum naponta) → Potentially Shippable Increment → Sprint Review + Retrospective → következő Sprint

Vízesés vs Scrum – összehasonlítás

Vízesés

  • Lineáris, egymás utáni fázisok
  • Teljes terv az elején
  • Szállítás a projekt végén
  • Megrendelő nem folyamatos
  • Változás drága és nehézkes
  • Fix határidős projektekhez

Scrum

  • Iteratív sprintek
  • Inkrementális tervezés
  • Szállítás minden Sprint végén
  • Megrendelő (PO) folyamatosan jelen
  • Változás természetes, befogadott
  • Változó/bizonytalan követelményekhez
